- **`ScrapDraft` 스키마의 `feedItemId @unique` 제약 및 `eventKey` 컬럼 정의 모순 (D9, R3.5, R4.2, R9.2, T1)**
  Research에서 기존 `ScrapDraft.feedItemId @unique`가 다중 출처에 부족하다고 지적했으나, 정작 D9·T1의 스키마 변경 목록에는 `feedItemId` 처리 방안이 빠져 있습니다. 다중 출처 NEWS 초안과 출처 기사가 아예 없는 CONCEPT 초안(R4.2)에서 `feedItemId`에 무엇을 넣을지(nullable 여부, 대표 1건 연결 여부), 그리고 R9.2(컬럼 타입/제약 변경 없는 추가 전용 스키마)를 어떻게 만족할지 정의되지 않았습니다. 또한 R3.5는 `ScrapDraft(kind NEWS, eventKey, conceptSlugs)` 저장을 요구하지만 D9·T1에는 `FeedItem.eventKey`만 있고 `ScrapDraft.eventKey`는 누락되어 있습니다.

- **청크 폴백 시 '이번 실행에서 처음 등장한 사건'이 청크별로 쪼개지는 리스크 (D1, R1.3)**
  배치 채점 실패로 청크 모드에 들어가면 모든 청크에 'DB의 최근 7일 `NewsEvent` 목록'을 동일하게 전달합니다(R1.3). 그러나 **이번 실행에서 처음 등장한 사건**은 아직 DB `NewsEvent`에 없으므로, 1단계의 `roundRobin` 배분으로 같은 사건의 기사들이 서로 다른 청크에 나뉘어 들어가면 각 청크가 서로 다른 `event` 키를 새로 생성해 중복 초안이 만들어집니다.

- **복수의 뉴스가 같은 미발행 개념을 참조할 때 `firstEventKey` 단일 참조의 한계 (D6, D7, D9, R4.3, R6.2)**
  `Concept`는 `firstEventKey` 하나만 저장하고, 개념 발행 시 이 키의 `NewsEvent.threadId`로만 양방향 링크(개념의 ③번 Bit 및 기존 뉴스 Thread 끝 백링크 Bit)를 겁니다(D7, R6.2).
  1. 사건 A와 사건 B가 모두 같은 PENDING 개념을 참조한 뒤 두 뉴스가 먼저 발행되면, 나중에 개념이 발행될 때 두 번째 뉴스(사건 B)에는 개념 백링크 Bit가 추가되지 않습니다.
  2. 첫 번째 사건(`firstEventKey`) 초안이 폐기(`DISCARDED`)·만료(`EXPIRED`)되고 두 번째 사건의 뉴스만 발행된 경우, `firstEventKey`의 `threadId`가 영구히 `null`이어서 개념 발행 시 관련 뉴스 링크와 백링크가 모두 누락됩니다.

- **편집 충돌(409) 검증의 비대칭성과 Cron 덮어쓰기(Lost Update) 경합 (D8, R7.1, R7.2, T4, T6)**
  D8은 인박스에서 "발행·저장할 때" `updatedAt`을 검사한다고 했으나, R7.1·R7.2·T6는 **Publish(발행)** 시의 409 처리만 명세하고 세그먼트/제목 편집 저장 및 폐기(Discard) 시의 버전 검사는 누락했습니다. 더 중요한 리스크는 반대 방향입니다. 오너가 인박스에서 세그먼트를 수정 저장한 직후, 이미 돌고 있던 cron(D8)이 수정 전 `segments` 배열에 늦은 출처 Bit를 덧붙여 DB에 덮어쓰면 오너의 편집 내용이 유실됩니다(cron 쪽 DB 업데이트에 낙관적 잠금 조건이 없음).

- **개념 생성 실패 및 상한 초과 시 `conceptSlugs` 정합성과 인박스 UI 오표시 (D5, D7, R3.5, R4.5, R4.6, R8.1)**
  1. 실행당 새 개념이 3개일 때 3번째는 `Concept` 행조차 만들지 않는데(R4.5), 뉴스 초안의 `conceptSlugs`(R3.5)에서 이 3번째 slug를 제거하는지 명시되지 않았습니다(남아 있으면 R8.1·R6.1 조회 시 없는 slug 참조).
  2. 개념 Sonnet 호출이 실패하면 `Concept`가 `PENDING + draftId 없음`으로 남고 뉴스 초안은 정상 생성됩니다(R4.6). 이때 인박스 뉴스 카드(D7, R8.1)는 `"Concept: {term} (draft pending)"`을 표시하지만, 정작 인박스에는 발행할 개념 초안 자체가 존재하지 않아 다음 실행에서 같은 개념이 다시 등장하기 전까지 오너가 해결할 방법이 없습니다.

- **늦은 출처(D8)의 본문 부족·호출 실패·조립 검증 규칙 및 후보 정렬 기준 누락 (D2, D8, R3.1~R3.4, R5.1~R5.3)**
  신규 사건 선정(R2.1~R2.4)과 달리 늦은 출처 단계(R5)에는 다음이 빠져 있습니다.
  1. 늦은 출처 기사가 본문 부족(`no_content`)이거나 Haiku 포인트 호출이 실패했을 때 `FeedItem` 상태 전이(`SKIPPED`/`FAILED`)와 실행당 상한(3회, R5.3) 차감 여부.
  2. 남은 출처 자리가 1개뿐인 OPEN 사건에 늦은 기사 2건 이상이 동시에 들어왔을 때(또는 전체 늦은 출처 후보가 5건일 때, R5.3) 점수순 우선순위 적용 여부.
  3. 늦은 출처 포인트에 대한 500자 절단·URL 제거·금지어·숫자 검사(R3.1~R3.4) 적용 여부, 그리고 출처만 추가되고 Bit 1(종합 요약)은 갱신되지 않아 요약과 출처 목록이 어긋나는 문제.

- **`NewsEvent` 키 충돌 시 출처를 `CANDIDATE`로 두면 매 실행마다 Sonnet 슬롯을 영구 소모하는 무한 루프 (D11, R2.4, R3.5)**
  R3.5에서 "같은 `eventKey`의 `NewsEvent`가 이미 있으면 트랜잭션 실패 → 로그, 출처는 `CANDIDATE` 유지"라고 정의했습니다. 그러나 이 시점은 이미 채점 시 기존 사건 매칭에 실패(또는 레이스 컨디션 발생)하고 **Sonnet 종합 작성 호출(슬롯 1개 소모)을 마친 뒤**입니다. 출처를 `CANDIDATE`로 두면 다음 실행에서도 똑같이 상위 사건으로 선정되어 Sonnet을 호출하고 다시 트랜잭션 단계에서 실패하며 실행당 사건 슬롯을 영구 잠식합니다.

- **사건당 개념 2개가 모두 발행 상태일 때 뉴스 링크 Bit 구조 불일치 (D4, D7, R6.1, R6.2)**
  사건당 개념은 최대 2개 추출됩니다(D4). 두 개념이 모두 이미 발행된 상태에서 뉴스를 발행할 때(R6.1) `New to this?` 링크를 **하나의 Bit에 합치는지, Bit 2개로 각각 추가하는지** 정의되지 않았습니다. 또한 뉴스가 먼저 발행된 뒤 두 개념이 시차를 두고 각각 발행되면(R6.2) 그때마다 뉴스 Thread 끝에 Bit가 1개씩 총 2개 붙게 되어, 발행 순서(R6.1 vs R6.2)에 따라 최종 Thread의 Bit 구성이 달라질 수 있습니다.

- **초안 만료(3일/7일) 기준 시각 및 만료 트랜잭션의 FK/고아 상태 리스크 (D5, D8, D10, D12, R4.4, R6.5)**
  1. 생성 후 만료 직전(예: 2일 20시간 경과)인 OPEN 뉴스 초안에 늦은 출처(D8)가 붙어 `updatedAt`이 갱신됐을 때, 3일 만료(D10, R6.5) 기준이 `createdAt`이면 새 출처가 붙자마자 만료 처리됩니다.
  2. 1단계의 만료 정리(cron)가 `ScrapDraft`를 삭제할 때 `NewsEvent=EXPIRED` 및 `Concept.draftId=null` 갱신(D12, R6.5)이 한 트랜잭션으로 묶이지 않거나 수동 삭제 경로에서 누락되면, `Concept`가 `PENDING + 죽은 draftId` 상태로 고착되어 R4.4(`PENDING && !draftId`일 때만 재생성) 조건에 걸려 영구히 개념 초안이 재생성되지 않습니다.

- **CLI 백엔드 직렬 호출 수(최대 9회+)와 입력 토큰(3배) 증가에 따른 배치 타임아웃 리스크 (Research, D1, D4, D11, T5)**
  1단계에서는 실행당 LLM CLI 호출이 최대 4회(채점 1 + 생성 3, 각 본문 6,000자)였으나, 2단계에서는 최악의 경우 **채점 청크 N회 + 늦은 출처 Haiku 3회 + 사건 Sonnet 3회(입력 최대 18,000자) + 개념 Sonnet 2회**로 프로세스 스폰 및 추론 시간이 2~3배 이상 증가합니다. `claude -p` 서브프로세스 직렬 호출 특성상 cron 워크플로 타임아웃이나 부분 완료 후 중단 시의 복구 경계가 명세되어 있지 않습니다.
